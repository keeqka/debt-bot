Telegram Mini App: AI-мониторинг личных финансов

Техническое задание для передачи в Claude Code. Приложение открывается из Telegram-чата двух пользователей, отслеживает долги, доходы и расходы, распознаёт чеки, оценивает финансовое состояние с помощью AI и присылает еженедельные и ежемесячные сводки прямо в Telegram.

Важное уточнение перед стартом: подписка Claude.ai (Pro/Max) и Claude API — это разные продукты с разным биллингом. Готовая подписка не даёт бесплатных вызовов API. Раздел «Стоимость AI» и пункт 2 в спорных местах объясняют, почему это всё ещё дёшево для 2 пользователей.

1Цели и Scope

Цель продукта

Дать двум пользователям (семья/пара) единую точку контроля над личными финансами: видеть долги и план их погашения, понимать структуру расходов, получать AI-оценку «здоровья» бюджета и продвигаться к финансовым целям — не выходя из Telegram.

Формат

Telegram Mini App (Web App), запускается кнопкой из чата/группы с ботом. Без отдельного сайта, без отдельной регистрации — авторизация через Telegram.

В scope (v1)

  • Учёт долгов, платежей по ним, 2 AI-стратегии погашения
  • Доходы и расходы: ручной ввод + распознавание чеков/скриншотов
  • Автокатегоризация расходов и разбивка по категориям
  • AI-оценка финансового статуса (шкала зелёный→красный)
  • Еженедельная и ежемесячная сводка в Telegram
  • Цели накопления с AI-стратегией и подсказками по банкам РК
  • AI-чат консультант с моделированием крупных покупок

Вне scope (v1)

  • Более 2 пользователей / мульти-тенантность / приглашения
  • Прямая интеграция с банками (Open Banking, парсинг SMS)
  • Инвестиционный портфель, брокерские счета, крипта
  • Нативные iOS/Android приложения вне Telegram
  • Автоматические платежи/переводы (только учёт, не выполнение)
  • Гарантированно актуальные ставки банков РК в реальном времени

2Пользователи и авторизация

Ровно два пользователя, оба заранее известны (жёстко прописаны через переменные окружения по их Telegram ID). Отдельной регистрации, паролей или email нет.

ШагМеханизмРезультат
1. Открытие Mini App Telegram передаёт initData (подписанную строку с user.id, username, auth_date) Frontend отправляет initData на backend при каждом запуске
2. Валидация подписи Backend проверяет HMAC-SHA256 подписи по секрету бота (см. раздел 8) Отклоняются поддельные/протухшие (>24ч) запросы
3. Проверка whitelist telegram_user_id сверяется со списком из 2 разрешённых ID в конфиге Любой третий получает 403 и экран «доступ не предоставлен»
4. Сессия Backend выпускает короткоживущий JWT (TTL ~1ч), фронт кладёт его в память (не localStorage) Дальнейшие API-запросы идут с этим JWT
Модель данных общая, не раздельная: оба пользователя видят все долги/доходы/расходы/цели — это семейный бюджет, а не два изолированных кабинета. Каждая запись хранит created_by для атрибуции «кто добавил», но фильтрации «только моё» в v1 нет. Обоснование — см. спорное место №1.

3Архитектура и рекомендуемый стек

Приоритет — бесплатный tier / open source везде, кроме самого AI-вызова (см. пометку ниже). Стек рассчитан на нагрузку «2 пользователя», поэтому выбраны решения без серверов, которые нужно администрировать.

Схема архитектуры

Frontend

free

React + TypeScript + Vite, shadcn/ui + Tailwind, Recharts (графики через shadcn charts), @telegram-apps/sdk для интеграции с Telegram WebApp (тема, safe area, haptics).

Backend / API

free tier

Supabase Edge Functions (Deno) для кастомной логики и AI-вызовов + автосгенерированный PostgREST для простого CRUD под RLS-политиками.

База данных

free tier

Supabase Postgres (500MB, более чем достаточно для 2 пользователей), Row Level Security ограничивает доступ 2 whitelisted ID.

Хранилище файлов

free tier

Supabase Storage (1GB free), приватный бакет receipts/, доступ через signed URL с TTL.

Хостинг фронтенда

free

Cloudflare Pages (или Vercel Hobby) — HTTPS, CI из git по умолчанию, без ограничений по трафику на этом масштабе.

Cron

free

pg_cron + pg_net внутри Supabase — расписание живёт в БД, без внешнего планировщика.

AI — единственный платный компонент

pay-per-use

Claude API (Anthropic) — оплата по токенам, отдельно от подписки Claude.ai. Для 2 пользователей с умеренным использованием (несколько чеков в день, пара AI-запросов, один чат в день) расход обычно составляет единицы долларов в месяц. Это единственная часть стека, которая не бесплатна по умолчанию — сознательное решение, т.к. альтернативы (self-hosted LLM) не дадут сопоставимого качества распознавания чеков и финансовых рекомендаций. Модель: Claude — сильная модель для сложных задач (стратегии, чат), лёгкая модель для рутинной категоризации, чтобы снизить стоимость.

5Экраны и UX

Компоненты — максимально shadcn/ui. Плавные переходы между экранами (view transitions / motion), графики — Recharts в обёртке shadcn chart. Статусный цвет (зелёный…красный) — сквозной акцент: полоса вверху дашборда, точка на аватарке, обводка карточки цели.

Mobile-first, не адаптив «сверху вниз»: Telegram открывает Mini App почти всегда на телефоне (шторкой на iOS, почти на весь экран на Android) — верстаем в первую очередь под узкий экран 375–430px, десктоп получает ту же раскладку растянутой по центру, а не отдельный дизайн.

Навигация — нижний таб-бар, не верхнее меню

5 основных экранов — в нижнем таб-баре (Дашборд · Долги · Финансы · Цели · Чат), как в нативном iOS-приложении, большим пальцем достать удобнее, чем до верхнего меню. «Настройки» — не отдельная вкладка, а иконка профиля/аватара в шапке, чтобы не занимать 6-й слот таб-бара. Иконки — lucide-react, дефолтный набор shadcn/ui, а не эмодзи.

Safe area / вырез и Dynamic Island

Отступы через env(safe-area-inset-top/bottom): таб-бар и шапка не должны залезать под системные зоны iPhone. Telegram WebApp дополнительно даёт viewportStableHeight для расчёта реально доступной высоты под шторкой.

Скругления в стиле iOS

На iOS Telegram открывает Mini App как шторку со скруглёнными верхними углами — важные элементы не прижимаем к самому верхнему краю. Карточки, модалки и таб-бар — крупный радиус (rounded-2xl/rounded-3xl), без острых углов, в духе нативных iOS-компонентов.

1. Дашборд (главный экран)

  • Статус-баннер: цвет + короткий AI-вывод («Расходы под контролем, долг сокращается»)
  • Stat-карточки: баланс, доход/расход за месяц, сумма долгов
  • Кольцевая диаграмма категорий расходов текущего месяца
  • Мини-график остатка долга по времени
  • Быстрые действия: + расход, + фото чека, спросить AI

2. Долги

  • Список долгов карточками: сумма, ставка, мин. платёж, прогресс-бар погашения
  • Добавление/редактирование долга, история платежей по нему
  • Переключатель «Оптимальная / Агрессивная» стратегия (см. раздел 6)
  • Таймлайн погашения по выбранной стратегии + итоговая переплата

3. Доходы и расходы

  • Единая лента транзакций с фильтром по типу/категории/периоду/автору
  • Ручное добавление (сумма, категория, дата, заметка)
  • Кнопка «Фото чека» → загрузка → экран подтверждения AI-разбора перед сохранением
  • Разбивка по категориям (donut + список с процентами)

4. Цели

  • Карточки целей с прогресс-баром и датой
  • AI-стратегия накопления: сколько откладывать в месяц, когда достигнете цели
  • Релевантные депозиты/накопительные счета банков РК с пояснением выбора

5. AI-чат

  • Чат в стиле Telegram/iMessage, знает текущее финансовое состояние без пересказа пользователем
  • Быстрые подсказки: «Могу я купить MacBook за ...?», «Как быстрее закрыть долги?»
  • Моделирование покупки — карточка-результат с влиянием на статус/цели, не просто текст

6. Настройки через аватар, не таб-бар

  • Управление категориями, базовая валюта
  • Время еженедельной/ежемесячной сводки, часовой пояс
  • Статус подключения бота, повторная привязка

6Бизнес-логика

6.1 Стратегии погашения долгов

Обе стратегии используют метод «лавины» (avalanche: сначала долг с самой высокой ставкой) — он математически минимизирует переплату по процентам. Отличие — в объёме дополнительного платежа сверх минимального.

Оптимальная

баланс
  • Порядок погашения: по убыванию ставки (avalanche)
  • На досрочное погашение направляется ~10–20% свободного остатка (доход − обязательные расходы − мин. платежи)
  • Сохраняется финансовая подушка
  • Более длинный срок, минимальная переплата по процентам

Агрессивная

скорость
  • Тот же порядок (avalanche) — переплата всё ещё минимизируется при данной скорости
  • На досрочное погашение направляется до 50–80% свободного остатка
  • Явно указывается, какие расходы предлагается урезать
  • Короткий срок, минимальная подушка — риск отмечается предупреждением в UI

Альтернативное определение (snowball — сначала маленькие долги ради мотивации) рассматривалось и отклонено по умолчанию; см. спорное место №3.

6.2 Шкала финансового статуса

5-уровневая шкала, а не бинарная зелёный/красный, чтобы избежать резких скачков между двумя соседними неделями.

СтатусУсловие (ориентир)Что видит пользователь
Зелёныйнорма сбережений ≥15%, долг/доход низкий, подушка ≥3 мес.Похвала + один совет для роста

Итоговый статус считает Claude (см. контракт в 7.3), а не жёсткая формула на бэкенде — это осознанный выбор, чтобы учитывать контекст (сезонность, разовые траты), а не только пороги.

6.3 Категоризация расходов

  • Каждый новый расход (ручной или из чека) проходит через AI-категоризацию (раздел 7.2)
  • Если уверенность < 0.6 — категория проставляется, но помечается как «уточнить», подсвечивается в ленте
  • Пользователь может переопределить категорию вручную в любой момент — это не отправляется на дообучение модели, просто обновляет запись

7AI-функции, промпты и контракты

Все AI-вызовы идут через Claude Messages API с принудительным structured output (tool-use с одним обязательным tool'ом, а не парсинг свободного текста) — это делает контракт стабильным для бэкенда. Ниже — назначение, сжатый системный промпт и схема ответа для каждой функции.

7.1 Распознавание чека / скриншота

Вход: изображение (base64, до 5MB) + список существующих категорий. Модель: Claude с vision.

Ты помогаешь разобрать чек или скриншот банковского перевода/платежа.
Извлеки магазина/получателя, дату, сумму, валюту и предложи категорию
из списка: {categories}. Если это не финансовый документ — верни
is_valid_receipt=false. Не придумывай данные, которых нет на изображении.
  "is_valid_receipt": true,
  "merchant": "Magnum",
  "date": "2026-09-10",
  "total_amount": 12450,
  "currency": "KZT",
  "line_items": [{ "name": "string", "amount": 0 }],
  "suggested_category": "Продукты",
  "confidence": 0.92

Результат всегда ведёт на экран подтверждения — автосохранение без просмотра пользователем запрещено (см. риски OCR в разделе 11).

7.2 Автокатегоризация (ручной ввод)

Лёгкая/быстрая модель — задача простая и частая, дешевле гонять на меньшей модели.

  "category_id": "uuid | null",
  "new_category_suggestion": "string | null",
  "confidence": 0.0
7.3 Оценка финансового статуса

Вход: доходы/расходы за 1–3 месяца, долги, платежи, остатки, цели. Запускается при открытии дашборда (с кэшем на день) и в составе еженедельной/месячной сводки.

  "status": "green | light_green | yellow | orange | red",
  "score": 0,
  "headline": "string, до 80 символов",
  "key_risks": ["string"],
  "recommendations": ["string"]
7.4 Еженедельная / ежемесячная сводка

Вызывается из pg_cron. Текст должен помещаться в одно сообщение Telegram (лимит 4096 символов, целимся в <700 для читаемости).

  "period": "week | month",
  "status_emoji": "🟢",
  "telegram_text": "string, Markdown, <700 символов",
  "top_category_changes": [{ "category": "string", "delta_percent": 0 }],
  "one_recommendation": "string"
7.5 Стратегия погашения долгов

Вход: список долгов (сумма, ставка, мин. платёж) + свободный остаток. Вызывается по кнопке и при существенном изменении входных данных (новый долг, платёж).

  "strategy": "optimal | aggressive",
  "payoff_order": ["debt_id", "..."],
  "monthly_plan": [{ "debt_id": "uuid", "payment": 0 }],
  "estimated_payoff_date": "2027-04-01",
  "total_interest_paid": 0,
  "explanation": "string"
7.6 Стратегия накопления на цель

Вход: цель, свободный остаток, действующие долги, bank_products (справочник РК передаётся как контекст, не как задача поиска в интернете — см. раздел 4).

  "monthly_contribution_needed": 0,
  "estimated_completion_date": "2028-01-01",
  "bank_product_suggestions": [
    { "bank_product_id": "uuid", "reasoning": "string" }
  ],
  "risks": ["string"]
7.7 AI-чат консультант + моделирование покупки

Системный промпт при каждом сообщении включает свежий финансовый срез (доход/расход за 3 мес., долги, цели, текущий статус) — контекст не хранится «в голове» модели между сессиями, а прикладывается заново, чтобы не устаревал. Для вопросов вида «могу ли я купить MacBook за 750 000₸» модель вызывает tool model_purchase_impact.

model_purchase_impact(item_name, amount, payment_type: "one_time"|"installments", installment_months?)
{ "new_status": "yellow", "months_to_recover_buffer": 2, "impact_on_goals": [...], "verdict": "string" }

Ответ рендерится как отдельная карточка результата в чате (см. экран 5), а не просто текстом.

  • Кнопка Web App в чате
  • initData → сервер
  • Проверка HMAC

Настройка

  • Бот создаётся через @BotFather: /newbot → токен в секреты Edge Function, не в код
  • /newapp регистрирует Mini App с URL фронтенда
  • В чате/группе двух пользователей — кнопка Web App или закреплённое сообщение с меню-кнопкой бота
  • Оба пользователя должны хотя бы раз написать боту /start — иначе Telegram не даст боту проактивно слать сообщения (weekly/monthly сводки)

Валидация initData

secret = HMAC_SHA256("WebAppData", BOT_TOKEN)
check = HMAC_SHA256(secret, data_check_string)
if check !== hash → 401
if now - auth_date > 24h → 401
if user.id not in [ID_1, ID_2] → 403
Тема оформления синхронизируется с Telegram через Telegram.WebApp.themeParams и colorScheme — светлая/тёмная тема DaisyUI переключается автоматически вслед за темой самого Telegram.

11Безопасность

  • Каждый запрос проверяет подпись initData и whitelist из 2 Telegram ID
  • RLS-политики Postgres запрещают доступ без валидного JWT, привязанного к одному из 2 user_id
  • Секреты (bot token, Claude API key, service-role key) — только в env переменных Edge Functions, никогда во фронтенд-бандле
  • Фото чеков — приватный Storage-бакет, доступ только по signed URL с коротким TTL
  • Cron-эндпоинты защищены отдельным service-секретом, недоступны без него даже с валидным пользовательским JWT
  • Rate limiting на AI-эндпоинтах (например, 30 запросов/час на пользователя) — защита от случайного цикла запросов и от расхода бюджета
  • Приложение не хранит номера карт, CVV, пароли от банков — только суммы и текстовые описания
  • Логи AI-запросов не пишут полный base64 изображения в постоянные логи (только метаданные)

13Ограничения

  • Жёсткий whitelist на 2 Telegram ID — добавление третьего пользователя требует изменения конфигурации, это не продуктовая функция
  • Нет прямой интеграции с банками — все данные вносятся вручную или через фото чека/скриншота
  • Точность распознавания чеков не гарантирована на 100% — обязателен экран подтверждения перед сохранением
  • Данные о банковских продуктах РК курируются вручную и могут устаревать — в UI показывается дата обновления и ссылка на источник, пользователю рекомендуется сверяться напрямую
  • AI-советы (стратегии, статус, чат) — вспомогательная информация, не являются формальной финансовой консультацией
  • Базовая валюта — KZT; мультивалютность поддержана в модели данных, но конвертация курсов в v1 не автоматизирована

15Acceptance criteria

Авторизация и доступ

  • Открытие Mini App любым из 2 пользователей проходит без ручного логина
  • Запрос с поддельной/протухшей initData отклоняется с понятной ошибкой
  • Третий Telegram-аккаунт получает экран «нет доступа», не видит данных

Долги

  • Можно добавить/закрыть долг, внести платёж, увидеть обновлённый остаток
  • Обе стратегии показывают разный порядок сумм и дату погашения при одних и тех же долгах

Расходы / чеки

  • Фото чека даёт заполненную форму подтверждения с корректными суммой и датой в >90% тестовых чеков
  • Ни один расход не сохраняется из фото без явного подтверждения пользователем
  • Ручной расход появляется в ленте и дашборде сразу после сохранения

AI-статус и уведомления

  • Статус на дашборде обновляется не реже раза в сутки и соответствует шкале из 6.2
  • Оба пользователя получают еженедельное и ежемесячное сообщение в Telegram в заданное время ±5 минут
  • Сбой отправки логируется и не роняет остальную функциональность

Цели

  • Для новой цели AI-стратегия рассчитывается и отображается без ручного пересчёта
  • Показаны минимум 1–3 релевантных банковских продукта РК с датой актуальности данных

AI-чат

  • Вопрос о покупке (например, MacBook) возвращает структурированную карточку влияния, а не только текст
  • Ответы учитывают актуальные цифры пользователя, а не общие советы

16Спорные места и решения по умолчанию

Эти пункты стоило бы подтвердить с пользователем до реализации, но чтобы не блокировать Claude Code — ниже зафиксировано разумное решение по умолчанию для каждого.

1. Общий бюджет или два изолированных кабинета?

По умолчанию: один общий «семейный» набор данных, видимый обоим, с атрибуцией автора записи.

Почему: контекст — конференция/чат на двоих, цели вроде «квартира» обычно общие; раздельные кабинеты усложнили бы AI-оценку статуса (пришлось бы решать, чей это статус).

2. Подписка Claude.ai vs Claude API

По умолчанию: отдельный ключ Claude API с оплатой по токенам; подписка Claude.ai используется пользователем отдельно для общения с Claude, но не даёт бесплатных вызовов внутри приложения.

Почему: это два разных продукта Anthropic с разным биллингом; технической возможности «прокинуть» веб-подписку в API не существует. При малом объёме использования (2 человека) стоимость токенов минимальна.

3. Что значит «оптимальная» и «агрессивная» стратегия?

По умолчанию: обе — avalanche (по ставке), различаются только долей свободного остатка, направляемой на досрочное погашение (см. 6.1).

Почему: avalanche всегда даёт меньшую переплату при любой скорости, поэтому оставлять его в обеих версиях логичнее, чем переключаться на snowball — который мотивационно приятнее, но математически хуже. Snowball можно добавить позже как третий вариант.

4. Актуальность данных о банках Казахстана

По умолчанию: курируемая вручную таблица bank_products с датой обновления и ссылкой на источник; AI выбирает из неё, а не «придумывает» ставки.

Почему: у Claude нет гарантированного доступа к живым ставкам депозитов РК; выдумывание цифр в финансовом контексте недопустимо. Более сложная альтернатива — Anthropic web search tool «на лету» с явной пометкой «требует проверки» — можно добавить отдельным этапом.

5. Базовая валюта

По умолчанию: KZT как основная валюта интерфейса; поле currency есть у каждой суммы на будущее, но автоконвертации курсов нет.

6. Хранение фото чеков

По умолчанию: Supabase Storage, приватный бакет, оригинал хранится постоянно (для пересмотра при споре по сумме), доступ только по подписанной ссылке.

7. День и время уведомлений

По умолчанию: воскресенье 19:00 (итог недели, перед планированием новой) и последний день месяца 20:00, часовой пояс Asia/Almaty — оба настраиваются в UI.

8. Backend: своя нода или Supabase

По умолчанию: без отдельного Node-сервера — Supabase Edge Functions покрывают всю кастомную логику, PostgREST — CRUD.

Почему: для 2 пользователей отдельный сервер — это лишняя эксплуатационная нагрузка (мониторинг аптайма, деплой) без выигрыша; serverless free tier с запасом покрывает нагрузку.
